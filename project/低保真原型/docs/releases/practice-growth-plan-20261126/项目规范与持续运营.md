# 项目规范与持续运营

## 一个项目怎样才算可以发布

每项目建立可审阅的内容包，至少包含下列内容。字段名和UI由实施时决定，本文件定义应具备的效果，不要求所有项目采用相同四步。

| 要素 | 应具体到什么程度 |
| --- | --- |
| 目标与职业关联 | 谁遇到什么问题、为什么需要这个产物；主职业、相关职业及各自具体工作；映射到确切技能，不只挂宽标签 |
| 前置与环境 | 建议基础、可替代准备、环境/版本、安装/账号/联网/费用要求、可用的离线或低配置路线 |
| 输入材料 | 实际能取得的CSV/日志/代码/需求/接口/配置；字典、范围、原始与派生处理、必要授权；小预览与完整文件分开 |
| 实践要求 | 完成什么、哪些决定由用户作、约束、可接受方案及不要求范围；所有依赖材料存在，不能只有一段情境 |
| 产物 | 文件/程序/查询/界面/规则/报告及格式，如何被接手者运行、复算或使用 |
| 验收与参考 | 必要要求、可观察证据、可执行检查及失败反例、参考实现或独立复算、开放部分的评价量规；不能只判字数和字段非空 |
| 提示与迁移 | 分层提示、示范与独立新输入区分；下一步补强、变式和新情境说明；不提前泄漏独立任务全部答案 |
| 来源与许可 | 任务作者、原案例参考、方法、真实数据/代码素材分别标明，记录用途、版本、权利、归属和教学改动 |
| 版本与维护 | 项目、数据、测试/量规、依赖环境版本及变更；维护人、审阅与试学记录、反馈入口和替代项目 |

来源质量按与任务的匹配和实际阅读判断，不设“凑三条来源”即通过。本站原创任务可以由合规材料与方法支持，不强制伪装成某机构原题。资料真实也不意味着本站的参考答案正确，参考和负例必须另行复算/复现。

## 来源展示的具体要求

现有数据质量项目确实参考了GDS真实支出报送案例，实际练习是DfT交通碰撞数据的教学派生。正文已说明二者关系，卡片“案例来自GDS”仍容易混淆出品方。建议写清四种身份：

> 本站设计练习｜数据：英国交通部STATS19｜案例参考：GDS支出报送质量改进｜方法：英国政府数据质量框架

所有新项目也分别显示“谁设计任务、事实案例来自哪里、实际输入由谁发布、用了什么方法”。不把方法引用写成机构认证，不将链接数量变成可信度分数。

来源后台记录发布者、题名、URL、材料身份、适用范围、上游版本/提交、原始发布日期、访问及复核时间、许可与声明文件、原文件哈希、派生处理和错误注入清单。原始文件、教学派生、参考结果各有身份，不能将注入的错误说成原机构真实数据缺陷。

公开可读不代表任意再分发。数据、代码、课程文字、图片和附带素材可以有不同许可。CC BY、相同方式共享、非商业、禁止演绎和软件许可分别处理；无法确认权利时先使用原创材料和外链或保留待核，不能自动复制整套课程。学习者自己的材料默认不成为公共素材，投稿须明确分享范围、拥有的权利和必要脱敏。

## 项目完成与能力证据

当前综合项目主要是判断与说明的教学工作表，检查字段、证据ID和提交快照，再由本人自检。这样的任务可保留为一种类型。扩展后需要分开呈现：

- 已提交：产物已保存，范围及版本明确。
- 自动检查结果：展示实际执行过的检查、环境、输入、失败与通过项。
- 本人复核：本人核对过程、贡献和限制。
- 其他人审阅：实际审阅者和意见；AI反馈、同伴反馈与领域审阅分别标明。
- 技能检验：复用现有独立检验和成长规则，不因一次项目提交自动授叶。

自动检查适合确定条件；开放判断用可见量规。量规可描述“缺少关键证据／在当前约束下成立／能解释并处理变更”，同时列明引用到的产物位置、尚缺证据和下一步。关键要求没达到，不能靠其他分项平均掩盖。公开测试能帮助学习，独立迁移要采用不同输入与必要反例；参考答案公开过的题不再宣称为未见过的能力检验。

AI提示以方法、定位、反例和追问逐层展开。若用户选择看完整示范，保留该学习状态，后续用新的独立材料观察迁移。AI可辅助评价，但不能替用户编造执行回执、贡献或判断全部能力；外发资料继续按现有选择和授权。

## 变式的准入标准

每个变式必须回答：相对原项目改变了哪个约束、需要新增什么判断、参考结果如何变化、原检查还是否适用。例子包括数据关联一对多、迟到数据、动作权限、网络失败、并发、需求改动、不同使用方与资源限制。

只换人名/公司名/配色或随机数字，可以作为新的输入，但不能宣传成新的能力家族。增加数据量也不是天然进阶，除非引入性能、分批处理或验证范围的新要求。

规则可生成的变式在经过验证的边界内抽样，并冻结实例ID、种子、材料、检查及量规版本。超出边界的AI新题成为待审候选。每个实例需有可复算的预期；部分参数组合没有合理解或改变业务规则时应拒绝生成。没有验证器的开放变式先经编辑审阅，不许用“生成成功”替代“可教学”。

## 持续内容发布流程

候选来源/用户缺口→编写项目说明→来源和权利核对→制作实际输入/参考/量规→技术复现与反例→内容与教学审阅→少量试学→正式版本→持续反馈/来源变化→修订、替代或退役。

初期一个小团队可以兼任多个角色，但每项目要有维护责任，正式发布前关键结果需有独立核对方式。现有编辑/审阅/发布与审计角色可以复用；项目专属候选、试学、版本和来源变化仍需建设，不假称后台已经有完整生产线。

建议每月整理一次覆盖缺口、用户卡点与候选，不要求每月强行发布固定数量。API/工具变化快的项目可建议每三个月复查，稳定基础材料可六至十二个月复查；严重错误、许可问题和真实失效即时进入复核。以上是拟运营制度，本轮没有安排自动任务。

链接404只是复查信号，不能自动断言旧项目错误。先检查合法快照、替代入口、材料可用性和影响；必要时停止新开，保留用户的合法成果和历史记录。许可限制导致材料需移除时，保留允许保存的记录与归属信息，给可继续的替代路线，不静默重写用户作品。

发布版本不可变。已开始任务冻结当时材料、测试和量规；新版本说明差异，用户可自主选择新尝试。退役不再允许新开，但旧任务在许可和安全边界内可回看，状态不能硬改回“已发布”。来源版本与任务版本分别记录，不能只换网页文本而让原成绩指向新依据。

## 数据怎样帮助模块发展

先收集为改进课程必要且可解释的情况：哪个步骤被主动标为不清楚、参考与实际是否冲突、材料打不开、环境失败、预计投入是否偏差、作品缺哪类证据。少量用户试做和具体反馈比单看点击或完成率更有价值。

不能由停留时长、频繁求助或放弃直接推断能力。推荐后续时让用户看到理由并可改选；没有证据的能力保持未知。对外分享作品、教师审阅和公开投稿另行明确范围，个人项目、私人问答与反思不默认进入公开库。

运营观察包括十职业及技能覆盖、重复题比例、材料可用情况、参考复算通过、待审/过期项目、用户能否独立完成和接手产物。不要把这些合成为没有依据的“项目可信度98%”或“职业胜任率”。

## 一个拟新增项目的完整规格示例

**主题：将虚构订单数据整理为可复核的客户与订单模型。** 主方向数据工程，相关方向数据分析。可参考dbt Labs Jaffle Shop DuckDB的合成seeds与测试，用具体版本及Apache2声明。

输入为customers/orders/payments，附字段和粒度；用户提交转换SQL、模型字典、关键质量检查、结果CSV和重跑说明。基本检查包括唯一/非空、关系、订单状态范围、合计及支付关联基数。开放评价看为何选这种粒度、哪些数据问题需上游确认、失败时是否应发布。

进阶变式加入重复支付、迟到状态或上游改字段，要求说明原模型受影响范围。独立迁移换新情境与材料。数据和参考计算必须先制作、核读许可并复现；当前只是规格示例，不把它当成已经可开始的新项目。
