## 2. 网络安全：建议增加的方向级说明

### 2.1 可直接采用的总览与范围

**建议总览：** 网络安全工作围绕组织的信息、系统与业务风险，识别需要保护的对象，设计和维护防护措施，发现异常、分析证据，并与业务和技术团队完成处置、恢复与改进。工作既包括事件发生后的响应，也包括事件发生前的权限、配置、漏洞和风险管理。

**建议范围：** 本站“网络安全”是探索方向，不是一个统一岗位名称。本页认证日志案例代表安全运营中的初步研判与交接。安全工程、应用安全、授权测试、数据安全和治理评估的任务不同；一个岗位可能承担其中几类工作，也可能只负责一部分。[O*NET职业活动](https://www.onetonline.org/link/details/15-1212.00)涵盖风险评估、控制实施、记录及人员协作；[NICE对职业、岗位与工作角色的区分](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center/resources/occupations-jobs-and-work)支持保留这种范围差异。两者是美国职业/工作框架参考，不据此推断国内学历或招聘门槛。

### 2.2 完整工作链：可作为方向说明，而非新增固定流程数量

1. **了解业务和资产。** 先知道系统服务谁、处理什么数据、关键依赖和负责人是谁，确认本次工作可以查看和操作的范围。
2. **识别并安排风险工作。** 汇总配置、权限、漏洞或评估发现；结合影响、暴露条件和业务限制安排优先顺序，而非只按扫描器分数排序。
3. **协同落实控制。** 与开发、平台、运维和业务负责人约定修复、访问控制、日志或防护变更，保留责任与验证方式。
4. **监测与分析。** 将告警和日志放回资产及业务语境，区分观察、解释、影响范围与尚缺证据；决定是否升级。
5. **授权响应与恢复。** 按组织预案由相应角色批准和执行限制、清理、恢复等动作，并保存行动记录；分析人员不一定拥有全部处置权限。
6. **复核与持续改进。** 验证控制和服务恢复，整理残余风险、经验及后续责任，更新规则、流程和培训材料。

前述链条是本站对职业活动与[NIST SP800-61r3的准备、检测、响应和恢复建议](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-61r3.pdf)的原创组织；实际团队可以并行、循环或划分给不同角色。事件响应指南并不覆盖全部安全设计或国内合规要求。

### 2.3 细分任务、产物和准备范围

| 可探索路径 | 常见任务与可观察产物 | 准备重点及边界 |
| --- | --- | --- |
| 安全运营与响应 | 维护检测依据、分诊告警、关联日志、升级与响应；产物可为带事件编号的时间线、影响范围、响应记录及复盘行动 | 网络/系统/身份与日志基础、证据定位、脚本整理、交接沟通；检测工具输出不是自动定案 |
| 安全工程与应用安全 | 将威胁和安全要求落实到设计、配置及开发验证；产物可为控制要求、配置核验、授权测试记录和修复复测单 | 软件与系统基础、访问控制、设计与测试；具体工具随服务类型变化 |
| 漏洞与授权测试 | 在书面范围内验证弱点，说明可复现条件、影响、整改和复测状态 | 必须先明确授权、数据使用和操作边界；漏洞发现与业务风险接受不是同一职责 |
| 治理、风险与评估 | 梳理资产和控制证据、推动风险处置、协调审核与安全意识活动 | 理解业务、政策、证据与沟通；本页不提供对某行业的法律合规结论 |

国内《网络与信息安全管理员国家职业技能标准（2020年版）》的网络/系统/应用防护、管理和处置部分可用于说明基础工作；它只是该职业和该版本的活动参考，不代表上述所有工程或评估岗位。参见[原标准PDF](https://he.nvq.net.cn/siteApp/upload/1072/upload/2021-11-29/2544/22281638174686078.pdf)正文第1、4–7页（PDF第4、7–10页）。

### 2.4 日常、协作、环境与成长的补充稿

**日常：** 平时可能检查资产与访问变更、核对暴露或修复状态、调试检测与日志、处理咨询并更新记录；事件期间再集中分诊、调查、沟通和恢复。具体比重取决于岗位分工，不能将所有安全岗位写成全天值守告警。

**协作：** 业务/资产负责人说明重要数据和可接受的中断；开发与运维落实控制和变更；响应负责人协调处置；需要时由隐私、法务或审计角色解释通知、证据和外部沟通要求。建议在页面明确“谁提供信息、谁执行、谁批准、谁复核”，而非只列角色名。

**组织与行业差异：** 甲方内部安全团队可能持续维护同一组资产和风险；服务提供方可能按客户授权与服务约定工作；产品安全团队更多进入开发生命周期。数据敏感性、业务连续性和外部约束会改变工作重点。这是框架到本站的工作场景归纳，不是招聘比例调查。

**成长：** 可以用“按规则整理并升级线索 → 独立负责一类检测或整改闭环 → 协调跨系统风险、验证控制效果并改进流程”表达责任增长。不要写固定晋升年限，也不要把能完成E1–E3交接等同能独立响应全部事件。

**建议保留并增加的真实产物类型：** 保留事件时间线和研判交接，方向介绍再说明资产/风险清单、整改与复测记录、控制验证和访问复核等产物的用途。若后续制作样例，使用本站原创数据，并标清负责人、证据、状态、残余风险和复核动作。

### 2.5 同源比较的建议短句

- 关注问题：怎样让系统和信息风险得到识别、控制与持续验证，异常发生后如何有依据地响应。
- 日常工作：维护控制与风险记录，检查异常和整改，协调授权处置并复核。
- 典型产物：风险/控制记录、验证与复测证据、事件分析和响应交接。
- 准备范围：系统和网络基础、证据与安全验证、风险表达及跨角色协作；再按细分方向深入。

现有“认证事件离线研判”保留为代表任务和首个体验，不再代替方向级短句。

## 3. 运维工程：建议增加的方向级说明

### 3.1 可直接采用的总览与范围

**建议总览：** 运维工程围绕信息系统的持续可用、安全运行与可恢复性，管理环境和配置，观察用户与系统信号，安排变更、备份和容量，处理故障，并通过自动化与复盘减少重复问题。

**建议范围：** 系统/网络运维、云与平台运行、交付自动化和SRE有交叉，也有不同责任。SRE强调用软件工程、服务目标和可靠性取舍改进运行；DevOps是开发与运行协作的一组实践，并不是所有组织都有同名独立岗位。本页发布后异常案例只展示变更与恢复验收。[O*NET系统与网络管理活动](https://www.onetonline.org/link/details/15-1244.00)提供更广的运行、配置、备份与支持范围；[Google SRE Introduction](https://sre.google/sre-book/introduction/)仅作为Google方法与分工参考，不能把Google的时间配比和制度直接写成全行业要求。

### 3.2 补足持续工作链

| 环节 | 用户应理解的具体工作 | 常见可回查产物 |
| --- | --- | --- |
| 接管与运行准备 | 确认服务依赖、责任、访问权限、配置及恢复前提，安排观测和支持 | 服务/依赖清单、配置基线、责任与升级路径 |
| 例行运行与变更 | 检查计划作业、补丁与证书，评估发布、扩容或配置变更的风险和兼容性 | 作业与变更记录、发布检查、回退或停止条件 |
| 观察与诊断 | 从用户影响及服务指标发现问题，关联系统、网络、依赖和变更证据 | 指标口径、告警与运行手册、诊断时间线 |
| 恢复与验证 | 采用已获授权的恢复方案，核验数据、服务与业务关键路径并继续观察 | 操作日志、恢复验收、未覆盖项与交接 |
| 预防和改进 | 演练备份恢复，检查容量与成本趋势，改进重复操作和故障机制 | 恢复演练记录、容量计划、自动化与复盘行动 |

此表是本站对已读职业活动和SRE实践的原创教学组织，不要求所有岗位由一人完成全部环节。备份任务执行成功、技术指标改善和业务恢复分别需要相应证据。[SRE服务目标章节](https://sre.google/sre-book/service-level-objectives/)支持从用户关注的服务行为定义可测量指标，不支持把演练中的某个错误率当通用生产门槛。

### 3.3 细分路径与准备范围

- **系统与网络运行：** 操作系统、网络、身份和配置、备份、故障定位与支持。先能读懂系统状态、判断影响并安全变更，再逐步增加自动化。
- **云与平台运行/交付自动化：** 可重复环境、配置与基础设施管理、发布流水线、资源与访问边界；具体平台和工具取决于组织。
- **可靠性工程：** 由服务目标、观测、性能和容量等问题驱动工程改进，通过代码减少反复人工工作，并与产品和开发讨论可靠性投入。
- **专项运维：** 数据库、存储或网络等方向需要对应技术基础及恢复验证；不能因完成一次HTTP回退案例，就宣称覆盖这些专项。

通用起点可以说明系统/网络与HTTP基础、脚本和版本管理、日志/指标解释、备份恢复、权限及变更记录。数据库、容器或某一云平台属于按目标服务进一步准备的内容，不强制罗列为所有入门岗位必须同时掌握的清单。

### 3.4 协作、环境与成长的补充稿

**协作：** 与产品/业务确认重要流程和服务期望，与开发核对变更和依赖，与安全人员核对访问和补丁风险，与数据或云平台人员确认恢复和资源责任。故障中还需让支持与业务知道当前影响、下一步和更新时间。

**环境差异：** 企业内部系统运行可能以环境维护和服务支持为主；对外在线服务更关注用户流量、延迟和持续变更；受托运行还受服务合同与客户窗口约束。是否轮班、值守、驻场、负责硬件或承担公有云费用，需要看具体岗位，页面不作统一保证。

**成长：** 可表达为“在指导下按手册完成检查与恢复 → 对一个服务的变更和稳定性负责 → 推动跨服务的可恢复性、容量与工程效率改进”。SRE、平台和系统专项是可能的深化方向，不是人人遵循的单线晋升。

**现有案例保留：** 三个5分钟窗口分别以1000、1000、800请求为分母，5/1000=0.5%、80/1000=8%、4/800=0.5%，算术正确。业务流程仍失败则不能宣布完整恢复的判断也已存在。这些应作为良好示例保留，新增内容围绕正常运行、预防与工程改进，不再重复修旧案例。

### 3.5 同源比较的建议短句

- 关注问题：系统怎样持续提供可用服务，并在变更或故障后安全恢复。
- 日常工作：管理环境与变更、观察服务、处理故障、演练恢复并改进自动化。
- 典型产物：配置和服务记录、运行手册、恢复验收、容量与可靠性改进依据。
- 准备范围：系统/网络、脚本、观测与诊断、变更和恢复；再按平台或服务深化。

## 4. IT实施交付：建议增加的方向级说明

### 4.1 可直接采用的总览与范围

**建议总览：** IT实施交付把业务需求和选定的技术方案落实到使用方环境，澄清范围与流程，完成适配、配置和集成，组织数据与业务验证，准备切换、培训及支持交接，并跟进系统投入使用后的问题。

**建议范围：** 本站“IT实施交付”是涵盖多类岗位的探索方向，不宜与一个国际职业代码或“迁移工程师”一一等同。业务应用实施、技术集成、云/基础设施迁移及用户采纳支持各有侧重；本页报名迁移演练仅代表其中一个交付片段。[O*NET Computer Systems Analysts](https://www.onetonline.org/link/details/15-1211.00)中的需求分析、流程/系统集成、测试和用户支持活动可作部分交叉参照；它不是国内全部实施岗位定义。[Microsoft Success by Design](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/success-by-design)说明Dynamics365实施跨越需求与方案、实现、上线准备和投入运行，属于厂商实践参考，不是所有产品必须采用的流程。

### 4.2 完整工作链与协作责任

1. **理解现状和目标。** 与实际使用者、流程负责人和项目负责人确认问题、当前流程、成功标准、约束与本期范围，记录仍待确认的假设。
2. **做适配和方案选择。** 对比产品能力与需求，明确配置可解决的部分、需要接口或开发的缺口，以及改变流程的影响；范围变更由有责任的人确认。
3. **准备环境并实现。** 协调身份、角色、网络、配置、接口与数据映射，保留环境差异及依赖。实施人员可能负责一部分实现，也可能协调专业开发或运维执行。
4. **演练与验证。** 使用代表性数据和角色场景检查端到端流程；迁移需核对映射、完整性和异常记录；业务用户参与UAT，技术检查不能代替业务认可。
5. **决定和执行切换。** 事前确认允许条件、阻断项、负责人、窗口、支持及回退前提；按计划执行并记录剩余风险。已产生新业务数据时重新评估回退及对账方式。
6. **支持使用与持续交接。** 围绕真实工作进行培训和演练，跟进初期问题，交出配置、已知限制、支持路径和待办责任，再转入持续服务或下一期改进。

这套链条是本站对不同活动的原创归纳，不是声称实施人员独自拥有需求批准、验收或上线决策权。Microsoft材料中的UAT、培训、切换准备和运行阶段支持相关方法；具体行业、合同和产品仍决定范围。

### 4.3 细分路径、产物与质量

| 可探索路径 | 主要关注 | 能看见的工作产物 |
| --- | --- | --- |
| 业务应用/功能实施 | 业务流程与产品配置是否适配，用户能否按角色完成工作 | 现状/目标流程、需求与适配差异、配置说明、角色UAT场景 |
| 技术实施与系统集成 | 环境、身份、接口和数据在系统之间能否正确协作 | 接口/字段映射、配置与环境记录、集成验证和异常处理说明 |
| 迁移与切换 | 数据和服务如何在限制窗口中切换，失败后如何处理 | 演练对账、切换清单、Go/No-Go依据及增量/回退方案 |
| 采纳、培训与交付支持 | 用户是否能在新流程中工作，问题由谁持续接住 | 按角色的操作演练、支持说明、已知问题和责任交接 |

以上路径可能合并在一个岗位，也可能由顾问、业务分析、开发、数据、项目管理和客户支持共同承担。大项目中的“负责一个模块”与小项目中的“跨多环节协调”，都不能直接写成高低等级。

**能力与准备：** 业务访谈和清楚记录是为防止范围与成功标准含糊；流程建模和需求追溯帮助检查是否交对东西；数据、接口、角色与环境知识帮助发现跨系统问题；测试和文档让别人能够复验；培训与问题交接帮助系统真正被使用。ERP/CRM、云、行业系统等产品知识需要按拟探索的方向准备，不把单一厂商证书写为全体实施人员的必需条件。

### 4.4 组织、行业、环境与成长的补充稿

**差异：** 甲方内部实施更可能持续维护业务流程和产品使用，乙方服务可能按项目范围和验收节点交付；SaaS应用、企业业务系统、基础设施与行业系统对配置、集成、数据、现场条件和培训的侧重不同。此处是工作场景归纳，不是统计结论。

**环境：** 需要协调客户人员、环境依赖、数据可用性、培训和切换时间；现场、远程、出差与非工作时间窗口均由具体项目安排决定，不泛化为所有岗位固定工作制。

**成长：** “在指导下完成配置、检查和清楚记录 → 对一个模块或业务流程的交付闭环负责 → 协调多方依赖、解决方案与采用风险”。更大的责任需要看可验收成果、风险判断和协作质量，不能只看操作过多少次导入。

**现有案例保留：** 600→600只是记录数；当前已经补有字段规则、可下载原件、完整摘要及新增M601后不可直接回切的前提。应保留这套边界，再补“本次迁移从哪个业务需求开始、怎样确认适配与培训、后续支持如何持续”，不再将技术迁移等同整个职业。

### 4.5 同源比较的建议短句

- 关注问题：选定方案怎样适配使用方业务，并被验证、采用和持续支持。
- 日常工作：澄清需求与差异，协调配置/集成、数据与UAT、切换、培训和交接。
- 典型产物：适配与配置记录、集成/验收证据、切换决定、用户与支持交接。
- 准备范围：业务流程、产品与技术基础、验证、文档、沟通和依赖管理；再按产品和行业深化。
